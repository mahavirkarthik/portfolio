HOW I APPROACH ENGINEERING

Tools are choices.
Trade-offs are the work.

I try to understand the constraint first, then choose the simplest design that meets it. Here are examples from my cloud, DevSecOps, observability and local LLM work.

SELECT A QUESTION01 — 07
01Why use Kubernetes Deployment for stateless workloads?

A Deployment manages the desired number of interchangeable Pods and continuously reconciles actual state with that desired state. It gives me rolling updates, self-healing through replacement Pods, scaling and declarative rollbacks. For stateless services, replicas can be replaced without needing stable identity or persistent local state. If a workload needs stable identity or storage semantics, I'd evaluate a StatefulSet instead.

02Why put a Service or load balancer in front of Pods instead of calling Pod IPs?

Pod IPs are ephemeral. A Kubernetes Service gives clients a stable virtual endpoint and distributes traffic across the selected healthy endpoints. For traffic entering the cluster, an Ingress or Gateway with a load balancer can add routing, TLS termination and shared entry-point controls. I would not expose every Pod directly because that couples clients to short-lived implementation details.

03Why Terraform or CloudFormation instead of creating resources manually?

Infrastructure as Code makes infrastructure reviewable, repeatable and version-controlled. It gives teams a change history, a plan or change set before execution, and a consistent way to recreate environments. The trade-off is that state, drift, secrets and module or template changes need disciplined handling. For AWS-native stacks, CloudFormation is a natural fit; Terraform is useful when I need a consistent workflow across providers and services.

04Why use both Checkov and TFLint in the IaC security scanner?

They address different parts of the review. Checkov focuses on policy and security misconfiguration checks across IaC. TFLint focuses on Terraform-specific static analysis, provider-aware rules and common configuration issues. They can overlap at the edges, so I would tune rules and deduplicate findings rather than count duplicate alerts as extra security. In the POC, their findings were inputs to a broader graph-based risk view.

05Why separate metrics, logs and traces in an observability stack?

They answer different questions. Metrics show trends and alert on numeric signals; logs preserve event detail for investigation; traces show a request's path and latency across services. In the Synefo POC I explored Prometheus for metrics, Loki for logs and Tempo for traces, with Grafana as the investigation surface. Correlating them with shared service and trace identifiers helps move from an alert to the relevant request and log context.

06Why run Qwen locally with vLLM, and where does KServe fit?

Running Qwen3-0.6B on my local RTX 4060 let me experiment with model serving without depending on a hosted inference endpoint, while keeping the model and test data on my machine. vLLM provides an efficient serving runtime and an OpenAI-compatible API. KServe is a Kubernetes model-serving layer that can manage inference deployments and their lifecycle. I experimented with vLLM and KServe/Minikube workflows; I describe this as a learning lab, not a production GPU platform.

07If you use AI heavily to develop, what engineering work is actually yours?

I use AI as a development accelerator for research, scaffolding, debugging, explaining unfamiliar code and iteration. I remain accountable for deciding what to build, understanding the architecture, selecting infrastructure and security boundaries, integrating components, deploying, testing behaviour, diagnosing failures and verifying the output. I won't pretend every line was typed manually. My ownership is the system and the engineering decisions, not a claim of unaided code production.
